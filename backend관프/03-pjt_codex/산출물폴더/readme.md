# 03-pjt — ThRead 구현 과정 및 학습 회고

> **프로젝트 주제:** AI 기반 도서 분석과 창작 지원 서비스의 반응형 웹 화면 구성  
> **구현 범위:** PDF 필수 요구사항 F301~F308, 심화 요구사항 F309~F311, 도서 API 연동 및 커뮤니티 기능 확장  
> **기록 기준:** 실제 구현 변경 내역, 기능 검사 결과, 이 폴더에 저장된 화면 캡처

이 문서는 프로젝트의 실행 안내와 별도로, 단계별 구현 과정에서 학습한 내용과 어려웠던 점, 문제 해결 방법, 회고를 정리한 문서이다. 실행 방법과 환경 설정은 프로젝트 최상위의 `README.md`를 참고한다. 아래 회고는 구현 기록을 바탕으로 정리한 초안이며, 제출 전 개인의 실제 학습 경험과 팀 협업 내용을 보완할 수 있다.

## 1. 프로젝트 개요

ThRead는 도서를 검색하고, 도서에 대한 감상을 쓰레드로 공유하며, 관심 도서를 계정별로 관리하는 서비스이다. 처음에는 HTML·CSS·Bootstrap을 활용한 화면 구성으로 시작했으며, 이후 실제 도서 API와 Python 서버, SQLite 저장소를 연결했다.

구현 순서는 다음과 같다.

1. PDF 요구사항과 제공된 스켈레톤 코드 분석
2. Navbar와 Hero 구성
3. 베스트셀러 Carousel과 AI 추천 영역 구현
4. 장르 목록과 인기 쓰레드의 반응형 배치
5. 메인 화면 결합 및 로그아웃 Modal 구현
6. 국립중앙도서관 API 연동
7. 베스트셀러 오버랩, 장르 Grid, 공통 도서 상세 구현
8. 체험 로그인과 글쓰기 흐름 개선
9. 서버 계정·DB 저장·게시글 관리 기능 확장
10. 정보나루 API 연동과 검증 결과 정리

### 사용 기술과 역할

| 기술 | 사용 목적 |
| --- | --- |
| HTML | 화면 구조와 의미 있는 콘텐츠 구성 |
| CSS | 폰트·색상·간격·오버레이·반응형 스타일 |
| Bootstrap 5.3.3 | Navbar, Grid, Carousel, Card, Modal, Tabs, Pagination |
| JavaScript | 검색, 상태 변경, 팝업, 글쓰기·수정·삭제, 비동기 요청 |
| Python 표준 라이브러리 | 정적 파일 및 API 요청을 처리하는 로컬 서버 |
| SQLite | 계정, 세션, 게시글, 좋아요, 관심 도서 저장 |
| 국립중앙도서관 ISBN API | 도서 제목·저자·출판사·ISBN 등 서지정보 조회 |
| 도서관 정보나루 API | 소장 도서관과 대출 상태 조회 연결 |

## 2. 1단계 — 요구사항 분석과 프로젝트 구조 파악

### 구현한 내용

PDF의 요구사항을 F301~F311 번호로 나누어 확인했다. 필수 화면은 Navbar/Hero, 베스트셀러, AI 추천, 장르 목록, 인기 쓰레드로 구분하고, 개별 HTML 파일에 구현한 뒤 `06-main.html`로 결합하는 순서로 진행했다.

제공된 `assets` 폴더에서 도서 표지, 장르 이미지, 게시글 이미지, 폰트의 위치를 확인했다. 추가로 전달된 파이썬 샘플은 화면 구성 자체가 아니라 국립중앙도서관 API를 호출하기 위한 참고 코드라는 점을 구분했다.

### 학습한 내용

- 프로젝트 전체의 서비스 소개와 이번 회차에서 실제로 구현해야 하는 범위는 구분해야 한다.
- 요구사항에 표시된 ‘필수’와 ‘심화’는 구현 순서를 정하는 기준이 된다.
- 같은 도서 서비스라도 화면 구현, 도서 정보 조회, 사용자 인증, 게시글 저장은 서로 다른 작업이다.
- 작업 전에 파일 구조와 이미지 경로를 확인하면 구현 후 경로 오류를 줄일 수 있다.

### 어려웠던 부분과 해결 과정

문서 제목에 Python이 포함되어 있고 API 샘플도 있어, 처음에는 API 코드를 완성하는 과제로 오해할 여지가 있었다. PDF의 목표와 파일별 요구사항을 대조해 이번 회차의 중심이 HTML·CSS·Bootstrap 화면 구성이라는 점을 확인했다. API는 필수 화면 이후의 확장 기능으로 연결했다.

### 새로 배운 내용 및 느낀 점

바로 코드를 작성하기보다 ‘어떤 결과물을 어떤 파일에 만들어야 하는가’를 먼저 정리하는 과정이 중요했다. 요구사항 번호와 구현 파일을 연결해 두면 누락된 기능을 찾고 결과를 설명하기도 쉬워진다.

## 3. 2단계 — Navbar와 Hero 구현: F301, F302

### 구현한 내용

- 로고의 `Th`는 흰색, `Read`는 `#fe4a51`로 구분했다.
- 로고와 메뉴에 제공된 폰트를 적용했다.
- Navbar를 투명한 배경과 절대 위치로 배치해 Hero 이미지 위에 표시했다.
- 화면 폭 576px 미만에서 메뉴를 토글 버튼으로 전환했다.
- Hero 배경 위에 어두운 오버레이를 넣어 글자의 가독성을 높였다.
- 모바일에서는 지정된 문구 뒤에서 줄바꿈이 나타나도록 했다.

### 학습한 내용

Navbar, 배경 이미지, 오버레이, 본문 텍스트가 겹치는 구조에서는 `position`과 `z-index`를 함께 고려해야 한다. 각 요소가 어떤 기준으로 배치되는지 정하지 않으면 메뉴가 배경 뒤에 가려지거나 오버레이가 버튼을 덮을 수 있다.

또한 Bootstrap의 `navbar-expand-sm`과 CSS 미디어 쿼리의 경계를 일치시켜야 화면 너비에 따른 전환을 일관되게 유지할 수 있다.

### 어려웠던 부분과 해결 과정

디자인 예시에는 로그아웃 메뉴가 있었지만, 실제 사용자는 로그인하지 않은 상태에서도 로그아웃이 보이는 점을 불편하게 느꼈다. 처음에는 확인창만 구현했으나, 이후 로그인 상태를 구분하고 비로그인 상태에는 로그인, 로그인 상태에는 로그아웃을 표시하도록 변경했다.

### 새로 배운 내용 및 느낀 점

예시 화면의 모양을 재현하는 것과 사용자의 현재 상태에 맞는 화면을 제공하는 것은 다르다. 메뉴 하나도 사용자 상태와 다음 행동을 고려해야 자연스러운 서비스가 된다는 점을 확인했다.

## 4. 3단계 — 베스트셀러와 AI 추천 구현: F303, F304

### 구현한 내용

베스트셀러는 총 12권을 4권씩 3개의 슬라이드로 구성했다. Bootstrap Carousel을 사용하고 자동 순환 간격을 설정했으며, 이전 버튼 없이 우측 Next 버튼만 표시했다. 표지 크기는 150×220px을 유지했다.

AI 추천 영역은 전체 폭을 80%로 설정하고 중앙에 배치했다. Bootstrap Grid로 이미지와 설명 영역을 7:5 비율로 나누고 수직 중앙 정렬했다. ‘활동 데이터 기반’ 문구에는 지정된 색상, 폰트, 글자 크기를 적용했다.

### 학습한 내용

- Carousel은 이미지 나열뿐 아니라 슬라이드의 활성 상태와 컨트롤 연결이 필요하다.
- Grid의 열 비율과 Flexbox의 정렬 기능을 조합하면 콘텐츠의 비율과 위치를 따로 조정할 수 있다.
- 고정 크기 이미지가 여러 개 배치되는 화면에서는 부모 너비와 간격을 함께 계산해야 한다.

### 어려웠던 부분과 해결 과정

150px 너비의 표지 네 장을 모든 화면에서 가로로 유지하면 좁은 화면에서 넘침이 발생할 수 있었다. 표지 크기를 무조건 줄이기보다 태블릿과 모바일에서는 한 슬라이드의 네 권을 2×2로 배치하도록 조정했다. 매우 작은 화면에는 1열 배치를 적용했다.

### 새로 배운 내용 및 느낀 점

반응형 화면은 데스크톱 화면을 축소한 결과가 아니라, 같은 정보를 화면 크기에 맞게 다시 배치한 결과라는 점을 배웠다. 필수 크기 조건과 작은 화면의 사용성을 동시에 만족시키려면 콘텐츠 묶음과 배치를 따로 생각해야 했다.

> 베스트셀러 순위와 AI 추천 표지는 과제 예시 자료이다. 이 프로젝트가 실제 판매 순위 API나 AI 추천 모델을 실행하는 것은 아니다.

## 5. 4단계 — 장르 목록과 쓰레드 카드 구현: F305, F306

### 구현한 내용

장르 목록의 기본 모드는 Flexbox로 구성했다. 일반 화면에서는 4열, 모바일에서는 1열로 배치했다. 이미지가 항목을 채우도록 하고, 장르명을 좌측 하단에 겹쳐 표시했다.

쓰레드는 Bootstrap Card를 사용해 이미지, 제목, 본문, 작성자, 도서명을 구분했다. 이미지 높이를 고정하고 카드 아래쪽에 작성자와 도서 정보를 배치했다. 일반 화면은 3열, 모바일은 1열이며, 페이지를 바꾸면 다른 글이 표시되도록 구현했다.

### 학습한 내용

- `flex-wrap`과 `calc()`로 열 수와 간격을 관리할 수 있다.
- 이미지 위 텍스트는 부모의 상대 위치와 자식의 절대 위치를 조합해 배치한다.
- 본문 길이가 달라도 카드의 하단 정보를 맞추려면 카드의 높이와 내부 정렬을 함께 설정해야 한다.
- Bootstrap 스타일을 바꿀 때는 CSS 명시도와 선언 순서를 고려해야 한다.

### 어려웠던 부분과 해결 과정

글마다 제목과 본문 길이가 달라 카드 높이가 불규칙해질 수 있었다. 카드의 동일 높이 설정과 내부 Flexbox를 적용하고, 본문은 목록에서 요약해 표시하도록 했다. 전체 내용은 제목을 눌러 별도 팝업에서 읽을 수 있도록 확장했다.

### 새로 배운 내용 및 느낀 점

샘플 문장이 짧을 때만 보기 좋은 레이아웃은 실제 데이터에 쉽게 흔들린다. 긴 제목, 긴 본문, 이미지가 없는 경우도 함께 고려해야 한다는 점을 배웠다.

## 6. 5단계 — 메인 결합과 Modal 구현: F307, F308

### 구현한 내용

개별 화면을 `06-main.html`로 결합하고 공통 CSS를 사용해 색상·폰트·간격을 통일했다. 로그아웃 메뉴에는 Bootstrap Modal을 연결했다. X, 취소, 팝업 바깥 클릭은 창만 닫고, 로그아웃 확정은 서버 세션을 종료하도록 했다.

### 학습한 내용

개별 페이지에서 사용한 `id`가 통합 화면에서 중복되지 않도록 확인해야 한다. Modal의 버튼과 대상 `id`가 맞아야 하며, 창을 닫는 동작과 실제 사용자 상태를 변경하는 동작은 분리해야 한다.

### 어려웠던 부분과 해결 과정

외부 Bootstrap 파일을 불러오는 구조는 네트워크 상태의 영향을 받을 수 있었다. CSS와 JavaScript를 프로젝트 내부에 저장해 컴포넌트가 외부 CDN 연결에 의존하지 않도록 변경했다. 다만 도서 API와 Google 지도에는 별도의 인터넷 연결이 필요하다.

여러 Modal이 이어지는 흐름에서는 앞의 창이 닫히기 전에 다음 창이 열리면 배경이 남거나 포커스가 어색해질 수 있었다. 로그인 창의 닫힘 이벤트 이후 작성창을 열도록 연결하고, 창을 닫은 후 배경 요소가 남는지도 검사했다.

### 새로 배운 내용 및 느낀 점

버튼을 눌렀을 때 화면이 바뀌는지만으로는 기능이 완성됐다고 볼 수 없다. 취소했을 때 기존 상태가 유지되는지, 다음 창이 자연스럽게 열리는지까지 확인해야 한다.

## 7. 6단계 — 국립중앙도서관 API 연동

### 구현한 내용

제공된 샘플의 요청 방식과 공식 문서를 참고해 ISBN 서지정보 API를 연결했다. 브라우저는 Python 서버의 `/api/books`로 요청하고, 서버가 인증키를 읽어 국립중앙도서관에 요청하는 구조로 구성했다.

제목·저자·ISBN 검색, 검색 결과의 페이지 이동, 도서 정보 표시를 구현했다. 검색창은 빈 상태로 시작하며 사용자가 검색하기 전에는 도서 API를 호출하지 않는다. ISBN 검색은 하이픈을 제거한 뒤 응답의 ISBN이 정확히 같은 항목을 선택한다.

### 학습한 내용

- 화면에서 원하는 정보와 API 응답의 필드 이름은 다를 수 있다.
- HTTP 요청 성공 여부와 실제로 사용할 수 있는 데이터가 반환됐는지는 따로 확인해야 한다.
- API 키는 화면 JavaScript에 직접 넣기보다 서버 설정으로 관리하는 것이 적절하다.
- 인증키가 들어 있는 URL이나 예외 문자열을 그대로 기록하면 키가 노출될 수 있다.

### 어려웠던 부분과 해결 과정

제목 검색은 비슷한 제목도 함께 반환했다. 제목 검색과 ISBN 검색을 구분하고, ISBN은 정확히 일치하는 결과를 선택하도록 처리했다. 공통 상세 화면에서 제목으로 조회할 때도 다른 책을 임의로 선택하지 않도록 일치 여부를 확인했다.

표지 URL, 페이지 수, 판사항 등 일부 항목이 비어 있는 응답도 있었다. 모든 정보가 있다고 가정하지 않고 대체 이미지나 ‘정보 없음’을 표시했다. 예정가격 역시 현재 판매가격과 같다고 단정하지 않고 등록 당시 정보라는 점을 안내했다.

### 새로 배운 내용 및 느낀 점

API 연동에서 중요한 것은 값을 받아오는 것뿐 아니라 정보가 없거나 기대와 다른 응답이 왔을 때 화면을 어떻게 유지할지 정하는 일이었다. 외부 데이터의 한계를 숨기지 않고 보여 주는 것도 서비스 품질에 포함된다.

## 8. 7단계 — 심화 화면 구현: F309~F311

### F309: 베스트셀러 오버랩

베스트셀러 영역 높이의 절반이 Hero 위에 겹치도록 배치했다. 화면 크기에 따라 카드 높이가 달라질 수 있어 `ResizeObserver`로 높이를 측정하고 CSS 변수에 반영했다. 음수 위쪽 여백을 사용해 문서 흐름을 유지하면서 AI 추천과의 간격도 조정했다.

**어려웠던 점:** 한 화면에 맞춘 고정 음수 여백은 모바일이나 글자 길이가 달라진 화면에서 겹치는 비율이 바뀔 수 있었다.

**배운 점과 회고:** 요소의 실제 크기에 따라 계산할 부분과 CSS만으로 처리할 부분을 구분해야 한다. 보이는 위치만 옮기는 방식과 문서의 실제 배치 간격을 바꾸는 방식의 차이도 중요했다.

### F310: 장르 CSS Grid

`grid-template-columns`, `grid-auto-rows`, `gap`, 행·열의 `span`을 활용해 크기가 다른 장르 타일을 배치했다. 필수 요구사항의 Flexbox 구조도 확인할 수 있도록 기본/심화 배열 전환 버튼을 제공했다.

**어려웠던 점:** 심화 Grid로 전부 바꾸면 F305에서 요구한 Flexbox 구현을 확인하기 어려웠다.

**배운 점과 회고:** 심화 기능은 기본 요구사항을 지우는 방식보다 기본 구조를 유지하면서 확장하는 방식이 적절하다. Flexbox는 한 방향의 배치에, Grid는 행과 열을 함께 설계하는 배치에 유용했다.

### F311: 공통 도서 상세

처음에는 「채식주의자」 상세를 구현하고, 이후 다른 책도 같은 경험으로 사용할 수 있도록 공통 상세 화면으로 확장했다. URL의 ISBN 또는 제목에 따라 도서 정보를 조회하고 배경·제목·서지정보·관련 쓰레드를 변경한다.

화면에는 최소 높이 100vh의 Hero, 좌측이 어두운 오버레이, 도서 제목과 소개, archive 아이콘을 포함한 담기 버튼을 배치했다. 오른쪽에는 도서관/쓰레드 탭, Google 지도, 관련 글 목록과 페이지 이동, 글쓰기 기능을 구성했다.

**어려웠던 점:** 검색 결과는 정보 팝업, 특정 책은 상세 페이지로 이동하면 사용자가 책마다 다른 방식을 익혀야 했다.

**배운 점과 회고:** 같은 종류의 콘텐츠는 가능한 한 같은 이동 방식과 화면 구조를 제공하는 편이 이해하기 쉽다. 한 권의 책에 맞춘 화면에서 URL과 데이터에 따라 재사용할 수 있는 화면으로 확장하는 과정을 경험했다.

## 9. 8단계 — 로그인과 글쓰기 UX 개선

### 확인한 문제

초기에는 상세 페이지 안에만 작성 버튼이 있어 메인에서 로그인한 사용자가 글을 쓰는 곳을 찾기 어려웠다. 비로그인 상태에서 글쓰기를 누르면 로그인만 되고, 다시 작성 버튼을 눌러야 하는 문제도 있었다.

### 해결한 내용

- 메인 쓰레드 영역과 도서 상세에 작성 진입점을 제공했다.
- 비로그인 사용자가 작성을 누르면 로그인 후 작성창으로 이어지도록 했다.
- 로그인을 취소하면 대기 중인 작성 동작도 취소했다.
- 관련 도서, 제목, 본문을 입력하고 공백만 있는 내용은 등록하지 못하게 했다.
- 글 제목을 누르면 전체 내용을 읽을 수 있도록 했다.
- 모바일에서는 하단에 검색·쓰레드·마이 페이지 바로가기를 추가했다.

### 학습한 내용

사용자 흐름을 ‘버튼 하나의 동작’이 아니라 ‘처음 의도한 작업을 끝낼 때까지의 과정’으로 바라보는 것이 중요했다. 로그인은 사용자의 목적 자체가 아니라 글쓰기나 담기를 위한 중간 단계인 경우가 많다.

### 새로 배운 내용 및 느낀 점

기능이 존재해도 사용자가 위치를 찾지 못하면 사용하기 어렵다. 처음 방문한 사용자, 로그인한 작성자, 검색 후 감상을 쓰는 사용자처럼 관점을 나누어 확인하면 개발할 때 놓친 불편을 찾기 쉬워진다.

## 10. 9단계 — 서버 저장과 계정 기반 커뮤니티

### 초기 구조의 한계

초기 체험 기능은 닉네임과 글을 브라우저의 `sessionStorage`에 저장했다. 빠르게 화면을 시험하기에는 편리했지만 탭이나 기기가 달라지면 같은 글을 공유하지 못했고, 닉네임만으로는 작성자 권한을 확실하게 구분할 수 없었다.

### 확장한 내용

- SQLite에 계정, 세션, 게시글, 좋아요, 관심 도서를 저장했다.
- 회원가입·로그인·로그아웃과 서버 세션을 구현했다.
- 체험 계정에서 작성한 기록을 유지한 채 회원 계정으로 전환하도록 했다.
- 수정·삭제 권한은 닉네임이 아니라 서버의 계정 ID로 확인했다.
- 다른 계정도 같은 서버의 글을 읽고 좋아요를 누를 수 있도록 했다.
- 최신순은 작성 시각, 인기순은 실제 좋아요 수로 정렬했다.
- 예시 글에는 배지를 표시하고 포함 여부를 선택하도록 했다.
- 마이 페이지에 내 글과 담은 책 목록을 추가했다.
- 이전 체험 글은 원본을 지우지 않고 현재 계정으로 가져올 수 있도록 했다.

### 어려웠던 부분과 해결 과정

**화면의 버튼 숨김만으로는 권한을 보장할 수 없었다.** 다른 사용자의 글에서 수정·삭제 버튼을 숨기더라도 직접 요청을 보낼 수 있기 때문에 서버에서도 작성자 ID를 검사했다.

**좋아요를 여러 번 눌렀을 때 중복 집계를 막아야 했다.** 사용자와 게시글의 조합을 중복 저장하지 않도록 하고, 좋아요 상태를 명시적으로 요청하도록 했다. 표시되는 숫자도 서버가 확인한 집계 결과를 사용했다.

**DB 연결을 사용한 뒤 정리하는 과정도 필요했다.** 검사 중 임시 DB 파일이 사용 중인 상태로 남는 문제가 있어, 트랜잭션 처리와 연결 종료를 함께 보장하도록 수정했다.

### 새로 배운 내용 및 느낀 점

저장 위치가 달라지면 기능의 의미도 달라진다. 브라우저 저장은 개인 화면의 체험에 적합하지만, 여러 계정이 함께 사용하는 서비스에는 서버의 공통 저장소와 권한 검사가 필요했다.

또한 체험 기능을 실제 계정 구조로 바꿀 때는 기존 기록을 어떻게 유지할지도 고려해야 했다. 새 기능을 추가하는 것만큼 기존 사용자가 작성한 데이터를 잃지 않게 하는 과정도 중요했다.

> 서버는 기본적으로 현재 컴퓨터의 `127.0.0.1`에서 실행한다. 같은 서버의 브라우저·계정 간 공유를 구현한 것이며 인터넷 공개나 다른 PC에 대한 네트워크 배포는 별도로 수행하지 않았다.

## 11. 10단계 — 정보나루 API와 외부 서비스 상태 처리

### 구현한 내용

국립중앙도서관 ISBN API와 별개로 정보나루의 소장 도서관 조회 및 도서관별 대출 상태 조회를 연결했다. 지역과 ISBN으로 도서관 목록을 조회하고, 결과에서 도서관을 선택하면 지도 위치가 바뀌도록 구성했다.

### 어려웠던 부분

ISBN API에서 도서 정보를 받는 데 성공하더라도 도서관별 대출 가능 여부까지 조회할 수 있는 것은 아니었다. 두 API의 제공 범위와 인증키가 달랐다.

또한 정보나루 키를 발급받았다는 사실과 API가 활성화됐다는 사실은 달랐다. 구현 시 실제 응답에서 `vitalizationErr`와 API 비활성화 메시지를 확인했다.

### 해결 과정

- 인증키를 각각 서버 설정에서 관리했다.
- 키 없음, 활성화 승인 대기, 정상 결과 없음, 연결 오류를 구분했다.
- 승인 대기를 도서관 검색 결과 0건으로 오해하지 않도록 안내했다.
- 정상 응답의 소장 목록과 대출 Y/N 처리는 테스트 데이터로 검사했다.
- 실제 소장·대출 데이터 검증은 활성화 승인 후 진행할 항목으로 남겼다.
- 대출 상태는 제공기관의 전일 기준 정보임을 안내했다.

### 새로 배운 내용 및 느낀 점

외부 API를 사용할 때는 성공 응답뿐 아니라 신청·승인·활성화 상태도 구현 과정에 영향을 준다. 사용할 수 없는 상태를 정상 결과처럼 보이게 하기보다, 사용자가 이유를 알 수 있도록 설명하는 것이 필요했다.

## 13. 기능 검사와 검증 범위

### 수행한 검사

| 구분 | 항목 수 | 주요 확인 내용 |
| --- | --- | --- |
| 실제 HTTP 서버·SQLite 검사 | 42 | 계정 생성, 로그인, 세션, 계정 간 글 공유, 작성자 권한, 수정·삭제, 좋아요, 정렬, 계정별 관심 도서, 재로그인 후 기록 유지 |

| **합계** | **72** | **기능 및 데이터 흐름 검사 통과** |

테스트 계정과 게시글은 격리한 임시 DB에 생성했다. 실제 사용자 DB에 검사 데이터를 넣지 않았다. 도서관 정상 응답의 일부 검사는 테스트 데이터를 사용했으며, 실제 키로는 활성화 대기 상태를 확인했다.

추가로 HTML의 중복 ID와 로컬 파일 경로, Python·JavaScript 구문, 프런트엔드의 API 키 미포함 여부를 확인했다.

### 검증 결과를 해석할 때 주의한 점

검사 코드가 통과한 사실과 사용자가 현재 실행 중인 브라우저에서 같은 결과를 보는 사실은 구분해야 한다. 서버 코드 변경 후 이전 프로세스를 계속 사용하거나, 다른 포트로 접속하거나, 브라우저에 이전 파일이 남으면 결과가 달라질 수 있다.

실제 브라우저의 모든 화면 너비와 터치 조작을 자동으로 검증한 것은 아니다. 아래 캡처는 특정 시점의 화면을 보여 주며, 모든 기능이 정상이라는 증거로 일반화하지 않는다.

## 14. 산출물 화면과 확인 사항

제목 검색 항목, 검색어 입력, 검색 건수, 도서 카드가 표시된 화면이다. 표지 정보가 없는 응답에는 대체 이미지가 표시된다. 이 캡처의 검색어는 촬영 당시 입력한 값이며, 첫 진입의 기본값은 빈 문자열이다.

### 14.3 쓰레드 영역 — 재확인이 필요한 캡처

작성 버튼, 정렬 선택, 예시 글 필터, 새로고침 버튼이 보인다. 다만 **‘지원하지 않는 요청입니다’라는 오류가 표시되고 글 목록이 비어 있으므로, 정상 동작을 보여 주는 최종 산출물로 보기 어렵다.**

현재 서버 코드에는 쓰레드 API가 구현되어 있다. 그러나 이 캡처만으로 실행 중인 서버의 버전이나 실제 요청 경로를 확인할 수 없으므로 원인을 단정하지 않는다. 이전 서버를 종료하고 프로젝트의 `run.bat`으로 다시 실행한 뒤, 접속 주소와 `/api/posts` 응답을 확인하고 정상 목록·작성·수정·삭제 화면을 다시 촬영해야 한다.

**지도에 특정 도서관이 표시되는 것만으로 해당 책이 소장되어 있거나 대출 가능하다고 판단할 수는 없다.** 실제 대출 상태는 정보나루 활성화 이후 조회 결과로 확인해야 한다.

## 15. 전체 회고

### 학습한 내용을 연결한 점

이번 구현은 HTML로 구조를 만들고 CSS로 꾸미는 단계에서 시작했지만, 실제 사용자 동작을 연결하면서 JavaScript의 상태 관리와 비동기 요청, Python 서버와 DB 저장까지 확장됐다. 화면, 요청, 저장소가 각각 독립된 문제가 아니라 하나의 사용자 작업을 완성하기 위해 함께 맞물린다는 점을 확인했다.

### 가장 어려웠던 부분

개별 기능보다 여러 기능이 이어지는 흐름을 맞추는 일이 어려웠다. 비로그인 사용자의 글쓰기 의도를 로그인 뒤에 유지하는 일, 체험 계정을 회원 계정으로 바꾸어도 기록을 유지하는 일, 다른 책에서도 같은 상세 화면을 제공하는 일이 그 예이다.

또한 외부 API에는 누락된 정보와 승인 상태라는 제약이 있었다. 화면에 표시할 수 있는 정보와 실제로 확인하지 못한 정보를 구분하는 과정이 필요했다.

### 새로 배운 것

1. 화면에서 기능을 숨기는 것과 서버에서 권한을 검사하는 것은 다르다.
2. 브라우저 저장소와 서버 DB는 유지 범위와 공유 범위가 다르다.
3. API 키 발급과 API 활성화는 구분해야 한다.
4. 반응형 구현에는 글자·이미지 크기뿐 아니라 정보 배치와 접근 경로가 포함된다.
5. 기능 검사 통과, 실제 브라우저 확인, 제출용 캡처는 각각 별도의 근거이다.
6. 기능을 확장할 때는 이전 사용자의 기록을 어떻게 보존할지도 고려해야 한다.

### 느낀 점과 다음 개선 방향

처음에는 요구사항의 요소를 빠짐없이 화면에 배치하는 것이 중심이었지만, 개선 과정에서는 사용자가 원하는 일을 실제로 끝낼 수 있는지가 더 중요한 기준이 됐다. 로그인이나 담기처럼 작은 기능도 상태 유지, 오류 안내, 다음 화면으로의 이동까지 함께 설계해야 했다.

다음 단계에서는 오류가 보이는 쓰레드 캡처를 실제 실행 환경에서 다시 확인하고 정상 화면으로 교체할 필요가 있다. 정보나루 승인 이후에는 실제 소장 도서관과 대출 상태를 추가 검증하고, 다양한 모바일 화면에서 메뉴·검색·글쓰기의 접근성과 배치를 확인해야 한다.
